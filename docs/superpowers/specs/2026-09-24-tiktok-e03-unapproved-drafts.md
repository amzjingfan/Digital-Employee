# TikTok E03 未批准分佣草案持久化设计

## 目标与事实边界

主管需要保留内部拟议的开发、履约、维护分佣计算，并看见不同已存草案是否引用同一订单。PRD 9.3 要求草案、订单范围和计算证据；PRD D6 尚未给出正式比例、冲突优先级与财务审批人，订单事实来源的授权也尚未验收。本阶段保存的是人工输入的不透明引用和拟议比例，不是订单事实、批准规则、应付账款或付款指令。

## 方案选择

采用追加式草案快照：一个草案对应一个订单范围，最多 100 个 `order:` 不透明引用，并保存达人池修订号、三名责任人、拟议规则版本和期限、三角色整数基点与 `evidence:` 引用。保存时重跑既有预检；责任未齐、比例不为 10,000 基点、规则过期或范围内重复时拒绝保存。所有草案始终标记 `unapproved`，没有审核、冻结、支付或外部发送路由。

比较过两种做法。唯一订单占用索引会让最早的未批准草案凭保存时间获得优先权，与未定的 D6 冲突；只留浏览器临时输入无法跨会话审查。故允许保存跨草案重叠提案，读取时动态标明 `saved_order_overlap`，之后由正式 D6 规则决定是否及如何排他。并发保存后再次读取仍会显现冲突，不把“保存成功”解释为订单被独占。

## 数据、权限和接口

`tiktok_commission_drafts` 使用同租户达人池和用户外键、强制 PostgreSQL RLS、仅运行角色 SELECT/INSERT 授权，以及拒绝 UPDATE/DELETE 的触发器。订单引用序列按输入顺序存为 JSON 文本；服务端用已有 Pydantic 格式限制，禁止原始订单、联系人、聊天或授权负载。保存请求带客户端生成的幂等键；同租户同键同内容重复请求返回原草案，异内容返回 409。草案保存当时的三责任人和达人池修订号，读取时与当前状态比较，以 `responsibilities_changed` 明示过期。

`POST /api/enterprise/tiktok/commission-drafts/{entry_id}` 保存单个已通过结构预检的内部草案。`GET` 同路径列出该达人草案及当前校验码。列表的重叠检测扫描租户内所有草案，包含其他达人；旧草案不会被静默删除或重写。现有多范围无状态预检接口保留。主管和租户管理员可读写；BD 不可读取分佣明细，服务层在宽泛 GET Casbin 授权之外再次拒绝。页面提供保存和历史/冲突提示，明确订单引用未经授权事实核验。

## 验收和后续门禁

测试覆盖幂等重试、同键异内容、跨租户隐藏、BD 拒绝、结构不合格、过期、责任变更、跨达人重叠和重读提示；迁移核对强制 RLS、同租户外键、仅 SELECT/INSERT 以及不可变触发器。隔离 PostgreSQL 验证运行时租户隔离与空安装逆向迁移。逆向迁移会删除草案表，只允许在确认没有需要保留的草案后执行；强制 RLS 下迁移角色不能可靠读取全表，因此逆向 SQL 不伪装成能自动证明表为空。正式比例、规则发布、订单事实授权、跨草案独占判定、具名财务审核与冻结快照均是下一阶段，不由本阶段保存结果推导。
