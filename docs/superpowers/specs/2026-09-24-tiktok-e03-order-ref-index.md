# TikTok E03 草案订单引用索引设计

## 目的与边界

已存未批准草案需要按同租户订单引用发现重叠。现实现读取一个达人时扫描租户内全部草案并反复解析 JSON；数据增长后成本随历史总量上升。PRD D6 的比例、优先级和审批人以及授权订单事实尚未确定。本切片只改进内部草案的重叠提示，不占用订单、不决定草案胜出，不增加审核、冻结或付款能力。

## 选择

保留现有不可变 `order_refs_json` 快照，另建由数据库维护的 `tiktok_commission_draft_order_refs` 明细表，以 `(tenant_id, order_ref, draft_id)` B-tree 索引供精确等值查询。读取某达人草案时，先用 `(tenant_id, pool_id)` 取目标，再将其订单引用并集批量查同租户明细，建立引用到草案 ID 的映射。SQLite 单元测试沿用同租户 JSON 扫描作为兼容路径。API 响应、输入结构和未批准状态保持不变。

明细行只能由草案 `AFTER INSERT` 触发器从不可变 JSON 快照生成；运行角色有 SELECT、没有 INSERT/UPDATE/DELETE 权限。触发器函数以受限迁移角色执行，并以当前租户上下文校验插入。明细表有同租户草案外键、强制 RLS、只追加保护和引用格式约束。正式财务分配以后仍需要经授权、可验证的规范订单键；本明细表只索引未核验的不透明引用。

## 迁移与并发验收

独立 v2 迁移创建明细表并回填既有草案。由于母表强制 RLS，迁移在单一事务内暂时赋予迁移角色 SELECT 策略、对子表暂时赋予 INSERT 策略，回填后均撤销，最后只留下子表受租户上下文约束的触发器写入策略；这些临时策略不会在提交状态出现。若既有 JSON 无效或重复，整笔迁移失败且不丢弃原草案。逆向迁移删除派生明细和触发器，保留原草案 JSON；再次前向迁移可重新回填。生产实施前仍需目标库门禁与维护窗口评估。

测试须证明：精确引用匹配、同租户跨达人重叠、跨租户隔离、空列表不查询全租户、PostgreSQL 查询走明细表等值索引；既有草案回填且临时策略不残留；两个独立事务可保存同一引用，双方提交后重读均见冲突。并发测试证明重读最终可见性，不承诺任一保存响应即时发现未提交的另一事务，也不构成独占。所有结果继续 `rule_unapproved` 且不能提交财务审核。
